01

Origin

The problem before the product

A student trying to find out whether a quota deadline has passed has to check four or six different institutional websites — the Entrance Exam Board, the Institute of Engineering, Tribhuvan University, and whichever campus they’re applying to — most of them Nepali-language PDFs behind a “click here,” dated in a calendar (Bikram Sambat) that nothing on the page converts for them.

Sarathi’s own about page states the actual thesis, and it isn’t a UX complaint: “Every year, students miss deadlines that were published correctly.” Nothing about that is anyone’s fault, and all of it is avoidable. That sentence is the whole reason this exists — everything below is what it took to make it true.

02

Commit 597b1cd

The skeleton

The first version of Sarathi, in the commit message that made it: “a minimal langgraph chatbot with chat loop.” No documents, no retrieval, no dates, no lookups — a model and a graph, talking to itself.

Nothing else in this document is a rewrite of that loop. It’s all additions to it, and every one of them was bolted on because the loop, left alone, did something a student couldn’t trust.

03

Retrieval

Grounding it in documents

The next thing built was retrieval: IOE’s notices and admission booklets, translated by hand into Markdown, chunked on their own headings, and embedded with a local model (bge-m3) into a Chroma vector store. A retrieve step in the graph fetches the nearest chunks to a question before the model ever writes a word.

This is what turned a chatbot into a RAG system — answers started coming from real institutional text instead of whatever the base model happened to know, which for a specific admission cycle in a specific country is approximately nothing. But grounding what the model reads doesn’t stop it from inventing what it can’t read. Two early bug reports proved that, back to back.

04

Issue 1

The rank it wouldn’t read

Asked who scored a given rank on the entrance exam — a fact sitting in a CSV of 7,179 published results, right there in docs/ — the bot refused:

The student asked for rank 13. The pass list had it.

Measured
To provide you with accurate information, I would need the
specific form number of the candidate who scored rank 13...
If no specific form number is provided, I cannot determine
who scored rank 13 based on the available data.

The pass list was in the index, technically searchable — but similarity search over names and roll numbers returns near-noise. A rank isn’t a “similar” kind of fact, it’s a specific row in a table.

The fix

Pull the pass list out of the vector index entirely. Regex the raw question for a form number or a phrase like “rank 13,” look it up directly in the CSV, and hand the model the exact record to restate as a sentence — results.py, no embedding involved. The model composes; it never searches for a fact this precise.

05

Issue 2

The date it invented

Asked what today’s date was, the model produced a fluent, plausible, entirely made-up answer:

Measured
Today's date in Nepal is 2083 Shrawan 9 (2026-07-15).

An LLM has no clock, and it’s worse at Bikram Sambat arithmetic than it is confident about being wrong. Confidently wrong reads identical to right, right up until a student misses a deadline trusting it.

The fix

Same shape as the rank problem: stop asking the model to know or calculate anything. dates.py computes today’s date in Kathmandu, converts it to BS, and resolves every BS date mentioned in the question or the retrieved text to its AD equivalent and a plain offset (“in 12 days,” “closed 12 days ago”) — in Python, before the model runs. It’s handed the finished numbers on every single turn and only ever asked to read them off.

The pattern that came out of these two bugs is the one this project has run on ever since: never ask a small model to know or compute something a few lines of Python can get exactly right. Compute the fact, and let the model write the sentence around it.

06

Issue 3

Becoming a product, not a demo

With the two worst lies closed, the next problem was trust of a different kind: it looked like a hackathon chat window, and a nervous 18-year-old checking a deadline reads “looks unofficial” as “might be wrong.”

This is where the admin console arrived — an actual UI for uploading and reindexing documents, instead of SSH and a script — alongside a live notices feed shown beside the chat, and a full editorial visual pass: the TU crest, a Devanagari subline, formal type. The backend was already correct by this point; this chapter is what made that correctness legible.

07

Issues 5 & 12

Citing its sources, honestly

Citations aren’t markers the model is asked to emit inline. A 7B model’s citation markers are wrong often enough that a citation which is sometimes there is worse than none — a student can’t tell a dropped marker from an answer that was never grounded at all.

Instead they’re computed after the fact: retrieval hands the prompt a set of candidate documents, and once the answer is written, each candidate is checked against it for shared distinctive vocabulary. Measured over real answers, a grounded answer shares 17–75% of its distinctive words with the source it drew from; a refusal shares 2–15%. The cut for “name this source” sits in that gap, and it errs downward — losing a citation costs a link the student can still find in the notices rail; inventing one puts a source under a sentence it never actually used.

08

Issue 13

The blind spot

Asked whether anything had been published that week, the bot said no — while the notices rail sitting right next to the chat was showing one from the day before. Four sites were already being scraped into a cache of 35 notices. The model simply had no way to see that cache; this wasn’t an internet-access gap, it was a wiring gap.

The first instinct was to index the notice pages themselves. Sampling one page per source killed that plan fast — every one turned out to be a heading over a scanned PDF. The richest page held 209 characters, and most of that was “Click Here” and “in pdf format.”

The fix

Index the record, not the page: title, both dates, publisher, link — a few lines the assistant can state with confidence, alongside a standing digest of the six newest notices injected into every prompt, so “anything new?” never depends on the question happening to name one. Two more campuses were added along the way (six sources total, 57 notices), with one near-miss caught before it shipped: cec.edu.np looked like Chitwan Engineering Campus and isn’t — it’s an unrelated consultancy. The real campus, cec.tu.edu.np, publishes no feed of its own.

09

Issues 6, 11, 14–18, 20

The interface grows up

A run of smaller, real bugs, each one closing a gap between what the UI implied and what actually happened: raw model output became rendered Markdown; a chat-history sidebar meant a conversation was never lost; refreshing the page used to re-ask the last question and quietly spawn a duplicate conversation, traced to the question living in the URL’s search params and fixed by handing it over out of band instead, the way a real chat product does it.

Scrolling had its own pair: reading back up mid-answer got yanked back down to the streaming text, and the fix for that briefly made a fresh answer look frozen because the follow-scroll was aiming at the wrong line — the sticky composer, not the actual foot of the page. And the whole thing read as flatly black-and-white until a second pigment was added on purpose: crimson only for a deadline with real consequences, lapis — Nepal’s blue — for anything the app itself contributes rather than quotes: the dates it computed, the labels it prints, the row you’re on.

10

Issue 19

Teaching it discipline in language

Asked to reply in Nepali, it wrote a fluent mix of Nepali and Hindi. Asked a plain question in Nepali, no instruction attached, it answered in Nepali — and invented syllabus subjects along the way. One rule already existed, buried sixty lines into the system prompt: “always reply in English.” The model never looked at it.

Four attempts at fixing this with better prompting followed, each one measured against the live bot rather than assumed to have worked — and each one failed differently:

AttemptResult
1The original buried rule, as shipped0 of 4 probes stayed in English
2Hoisted into its own section, told to refuse then answerWrote the refusal itself — in Nepali
3“Copy this exact refusal sentence, then answer”12/12 stayed English, but 3/12 sent only the sentence and stopped
4“The refusal is already handled, ignore the request”6 of 18 — mostly back to Nepali

The pattern across all four: naming the language request inside the prompt is what kept it alive, no matter how the instruction around it was worded.

The fix

Stop naming it. The “reply in Nepali” clause is stripped out of the question with a deterministic check — a language name alone doesn’t count, it takes a language and a speech verb, so “is the exam set in Nepali?” survives untouched. A question written in Nepali is translated to English before the model reads it at all, which removes the thing being mirrored instead of asking the model not to mirror it. And the one refusal sentence, when someone explicitly asks for another language, is written by the app — fixed wording that can’t drift and can’t be mistaken for the whole reply. Final score: 24 real turns across 8 cases, every one answered, every one in English.

12

Design decision

Why this isn’t an agent

LangGraph supports tool-calling, and qwen2.5:7b does too — Ollama reports it as a model capability. Sarathi doesn’t use it. Not because it’s unavailable, because every failure chronicled above is what a missed or malformed tool call looks like:

Decided by Python, every turn
  • Whether a form number or rank is in the question
  • What today’s date is, and every BS↔AD conversion in play
  • Whether the notice feed needs refreshing
  • Whether the question asked to switch language
Decided by the model, once
  • How to phrase the answer, from facts it was already handed

Tool-calling would turn every one of the Python column’s rows back into a judgment call the model has to get right on every single turn — whether to call a tool, which one, with what arguments — and this document is a long list of that exact model failing plainer instructions than that. Issue 13’s original bug, the bot flatly denying a notice existed, is a tool-selection failure by definition: the question didn’t look notice-related, so nothing would have fired. Injecting the digest into every prompt doesn’t ask for that judgment; there’s no decision left to get wrong.

There’s also a plainer cost: a local 7B model is already the slow part of every turn, and a tool call is a full extra pass through it. None of this is a permanent verdict — it’s specific to a small local model answering from a bounded, trusted set of facts. If the model tier goes up, or the set of things worth fetching stops being a short fixed list and starts being genuinely open-ended, this is the chapter worth reopening.
